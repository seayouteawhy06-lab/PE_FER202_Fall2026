## **1. Overview** 

You will build **ShelfLife** , a small web app where each person keeps a list of the books they want to read, are reading or have finished, and sees how much they have on their shelf. It uses what you learned: a Next.js project with Tailwind CSS and ShadCN UI, forms with validation, React Context for shared state, Supabase for login and for the database, and a deployment on Vercel. 

This exam describes **what the app must do** , not how to code it. How you structure the code is up to you, as long as the routes, the visible texts and the <mark>data-testid</mark> names in this document are exactly as written. 

## **2. The application** 

### **2.1 Setup** 

- A Next.js project (App Router) with Tailwind CSS and ShadCN UI ( <mark>components.json</mark> in the project root, at least **two** ShadCN components actually used). It must build with <mark>npm install</mark> followed by <mark>npm run build</mark> using only two environment variables: <mark>NEXT_PUBLIC_SUPABASE_URL</mark> and <mark>NEXT_PUBLIC_SUPABASE_ANON_KEY</mark> . No key may be written directly in the code. 

- In your Supabase project: turn **off** “Confirm email” (Authentication → Providers → Email) so new accounts work at once, create one **test account** for the grader, and set up the database as described in section 2.2. 

### **2.2 Database (Supabase)** 

Design the database yourself in your Supabase project (SQL Editor or Table editor) and save the SQL you used in your project as <mark>supabase/books.sql</mark> . Create **one table named books** that stores everything the app saves. It must have **at least** the columns below. The **column names must be exactly as written** , because the grader reads and writes them through your project's API; you choose the data types, defaults, constraints and indexes. 

|**Column**|**What it holds**|
|---|---|
|id|a unique id for each book|
|user_id|the person the book belongs to (the logged-in user's id)|
|title|the title of the book|
|author|the author of the book|
|pages|number of pages|
|status|one of To Read, Reading, Finished (To Read by default)|
|created_at|when the row was added (used for “most recently added first”)|



**The database itself must refuse bad data** , not only your forms. The grader sends rows that break these rules straight to the API and expects an error each time: 

- <mark>title</mark> is required (spaces only does not count) and at most 80 characters. 

- <mark>author</mark> is required (spaces only does not count) and at most 60 characters. 

- <mark>pages</mark> must be a whole number from 1 to 5000. 

- <mark>status</mark> must be one of the three values above; anything else is refused. 

**Security rules.** Turn on Row Level Security on the table and write the policies yourself so that: 

- a person who is logged in can see and change **only their own** rows (read, add, change the status, delete) and nothing else; every row belongs to the person who saved it; 

- a row whose <mark>user_id</mark> is another person's id is rejected when it is saved; 

- a visitor who is not logged in can neither read nor write anything. 

Allow only the actions the app really needs, and never switch row-level security off or use the <mark>service_role</mark> key in the app. 

### **2.3 Pages and what they do**

### **Register — /register  and  Login — /login** 

- Same behaviour as Labs 2 and 3 (forms with your own messages, not the browser's — add <mark>noValidate</mark> ; nothing is shown before the first submit; an error disappears when its field becomes valid). Register has email, password and confirm password; Login has email and password. 

- With valid input, Register creates a **real** Supabase account and shows form-success (text **Registration successful** ); Login signs in for real and goes to <mark>/books</mark> . If Supabase refuses (duplicate email, wrong password) its message is shown in <mark>error-auth</mark> . 

|**Field**|**When**|**Exact error message**|
|---|---|---|
|Email (both forms)|empty / not a valid e-mail|Email is required/<br>Please enter a<br>valid email address|
|Password (both forms)|empty / fewer than 6 characters (Register<br>only)|Password is required/<br>Password<br>must be at least 6 characters|
|Confirm password<br>(Register)|empty / different from password|Confirm password is required/<br>Passwords do not match|



**Books — /books** (protected) 

- A visitor who is not logged in is sent to <mark>/login</mark> . While the app is still finding out whether someone is logged in, nothing from this page is shown (no flash of content, no wrong redirect). A logged-in person sees the page with <mark>books-page</mark> . 

**A. Add a book.** A form <mark>( book-form</mark> , <mark>noValidate</mark> ) with: title, author, number of pages, and status (a list with an empty first choice “Choose status”, then To Read, Reading, Finished). Validation runs when the form is submitted; nothing is shown on first load; each message disappears when its field is valid. 

|**Field**|**Rule**|**Exact error message**|
|---|---|---|
|Title|empty or spaces only / longer than 80<br>characters|Title is required/<br>Title must be at<br>most 80 characters|
|Author|empty or spaces only / longer than 60<br>characters|Author is required/<br>Author must be<br>at most 60 characters|
|Pages|empty / not a whole number from 1 to 5000|Pages is required/<br>Pages must be a<br>whole number between 1 and 5000|
|Status|nothing chosen|Please choose a status|



- With valid input the book is saved in Supabase for the logged-in user, appears in the list **at once without reloading the page** , the form is cleared, and book-success shows **Book added** . If Supabase returns an error, show it in <mark>error-book</mark> and do not add anything to the list. 

**B. The list.** All the user's books, most recently added first. Each book (book-item) shows its title, its author, its pages written as the number followed by **pages** (e.g. 320 pages), its status (exactly To Read, Reading or Finished), a Delete button, and — unless the book is already Finished — an “advance” button that moves the status one step forward: To Read → Reading → Finished. Advancing is saved in Supabase and the item updates at once; Delete removes the book from the list and from 

Supabase. After a page refresh the list is exactly the same. When there is nothing to show, display books-empty with the text **No books found** instead of the list. 

**C. Filter, search and summary.** Both work on what is on screen and update immediately (no button to press): 

- A status filter (All, or one of the three statuses) and a search box that keeps only books whose title **or** author contains the typed text (not case-sensitive, spaces at both ends ignored). They combine (both must match). A Clear button resets both. When a book's status changes so that it no longer matches the status filter, it disappears from the list at once. 

- The summary always describes **the books currently shown** : the number of books ( <mark>book-count</mark> , plain integer), the total number of pages ( <mark>total-pages</mark> , plain integer, 0 if none) and a breakdown with one row per status that appears, the status with the most books first (equal counts: To Read, then Reading, then Finished), each row showing the status name and how many books have it. 

### **2.4 Shared state** 

- The books are loaded once after login and kept in **React Context** , so the form, the list, the filters and the summary all use the same data without passing it down as props. After logout (and when another person logs in) the previous person's books must disappear from memory and from the screen. 

### **2.5 Look and feel** 

- At a phone width of 375 px there is no horizontal scrolling and the form and list are readable; at 1280 px the form and the summary can sit next to the list. Use Tailwind CSS and ShadCN UI (Button, Card, Input, Label … at least two used).
